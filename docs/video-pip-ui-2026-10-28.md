# PiP 转场与缩放监听

范围：首次进入 PiP 的白底图标、放大缩小时画面卡顿、UI 主线程卡帧。保留后台 AUDIO 禁用视频轨道；不加入解码器预热、后台持续解码或延迟关闭视频轨道。仅电脑 emulator-5554、测试包 `com.pixel.gallery.viewertrace`，不安装手机、不提交。

## PiliPlus 最终方案核对

直接读取当前 PiliPlus 的 `PipCoordinator.kt`、`PipRenderHost.kt`、`pip_source_rect.dart`、`pip_viewport.dart`，以及 `diagnostics/pip-20261007/FIXED-ROOT-ONLY.md`。最终保留原尺寸画布，通过已有 Android View 的缩放和裁切适应 PiP，锁定进入前视频区域，不更换播放器或视频输出。参照提交 `d0b40bfce`、`c32532a24`、`bacab3022`，未沿用已撤销的图层/解码器实验。

本项目实现采用相同原则，但 Compose 页面返回时不能强求系统栏边距等于进入前：播放器在 PiP 中可能自动隐藏控制栏，正常返回边距可以改变。第一版回归发现此条件导致布局未解锁，已删除边距相等门槛，保留退出状态及正常窗口尺寸门槛。

## 实现

- `VideoPipHost` 保持已有 Compose 页面及视频输出尺寸；系统 PiP 调整大小时只改变既有 View 的变换与裁切。正常模式照常测量布局。
- PiP 中保持原有 Configuration 和内容边距，退出恢复正常尺寸后解除。Android 15+ 使用转场通知；旧系统提前保存配置，窗口缩小时保护原尺寸。
- 视频布局/绘制前检查实际可见区域，及时更新 sourceRectHint；进入后不让小窗坐标覆盖原矩形。参数相同不重复发系统调用，明确启用 seamless resize。
- 监听 `VIDEO_PIP_PARAMS`、`VIDEO_PIP_HOST`、`VIDEO_PIP_UI`、`VIDEO_PIP_MODE`；沿用 FRAME_ACTUAL、FRAME_STATE、VIDEO_FRAME、音频欠载、Surface 生命周期。监听开关沿用测试构建开关。

## 证据

目录：`scratch/viewer-trace-captures/pip-ui-20261028-220716`。完整 logcat 独立进程实时写电脑，系统跟踪与图层跟踪分开保存。模拟器上的自建跟踪文件只有在拉取并核对 SHA-256 后才删除，电脑原始记录保留。

`baseline-valid-20261028-222410`：按钮进入与 HOME 自动进入，各 4 次双击缩放、返回原窗口，状态断言通过。随后“最近任务再回桌面”未进入 PiP，测试超时；此路径不记作通过。第一份 `baseline-20261028-221953` 的 logcat 有效，但 Perfetto 配置路径被系统拒绝，不能用于系统跟踪结论。

8 次缩放：UI 最长单帧 175–465ms；视频帧回调最大间隔约 59–83ms；没有解码器初始化、输出重新绑定或 Surface 销毁，没有音频欠载记录。此结果与用户“画面卡，声音不断”相符，但解码回调不等同于显示屏呈现。

`home_resize_0` 系统跟踪：主线程 `traversal` 302.10ms，包含 `measure` 102.48ms、`layout` 54.62ms、窗口 relayout 54.43ms；测量内有文本布局。不是播放器整体暂停，而是窗口尺寸变化引发原页面重新测量、布局及绘制。不能把 FrameMetrics 的 unknownMs 全部当成解码时间。

`baseline-layers-20261028-222317/layers.perfetto-trace`：系统 `PipContentOverlay` 有 48 个图层快照，其中 37 个可见。`fixed-layers-20261028-223043/layers.perfetto-trace` 中没有该图层；有 PiP 菜单图层及 391 个可见视频 Surface 快照，说明并非没有进入 PiP。该对照针对首次 HOME 进入；不是手机全场景物理画面验收。

第一版 `fixed-20261028-222804`：4 次双击缩放时视频输出尺寸不变，UI 最长单帧约 87–198ms；返回时因边距门槛导致布局未解除，此版作废为最终产物。原始系统跟踪有 32 个排序健康告警，不能称跟踪完全无异常。

## 后续修正：统一缩放及验证实际可见画面

上一阶段把应用 Window 的长帧直接用来判断 PiP 视频是否停住，证据不足。视频由独立 Surface 合成，应用 UI 帧、解码回调、合成器实际可见缓冲帧必须分别记录。现新增 `capture_pip_complete.py`：全量 logcat 独立写电脑；系统跟踪同时记录实际图层边界、可见性、缓冲帧号，生成期间持续传到电脑，结束后另拉完整文件并校验 SHA-256，校验相同后才移除模拟器临时文件。电脑原始文件不覆盖。

- `before-transform-20261028-231015` 与 `transform-only-20261028-231210` 使用相同操作。12 次缩放中的 Compose 重组从 12 次变成 0 次；系统仍可调用 View 的测量入口，不应称所有测量回调消失。应用 Window 仍有长帧，不能将此统计替换成视频停顿结论。
- PiP 期间暂存窗口配置与边距，返回正常窗口再交付；内容确实请求布局时仍处理。使用原有页面和视频 Surface 的变换、裁切，不新增动画、位图、解码器或后台持续解码。
- `landscape-paused-20261028-232019` 进一步发现上一阶段 `VideoPipHost` 的真实缺陷：正常页面为 1080×2400，而横向 PiP 放大后为 996×560。旧判断要求宽、高同时小于原来的 90%，导致错误地复原画面变换，视频落在窗口之外。合成器记录显示空的屏幕边界；单靠 `isPlaying`、`isBuffered` 会漏报。该版本作废。
- 修正为按窗口长、短边共同判断是否恢复正常尺寸；接近屏宽的 PiP 仍只缩放原画面。此判断也允许从 PiP 返回已改变屏幕方向的正常窗口。
- 新增实际 View 可见区域断言，及播放中双击、捏合，暂停后双击，恢复播放、返回原任务的用例。`scratch/pip-visible-regression-before-logcat.txt` 记录了旧实现触发 `Playing surface is clipped outside the window`。该次进程退出由测试断言在主线程抛出造成，不是另发现的产品自发崩溃。
- `original-landscape-20261028-232222` 为最初未固定视频尺寸的版本；手动路径每次缩放都会发生 Surface 尺寸改变，捏合缩小记录到 119ms 的可见缓冲帧间隔。HOME 路径未进入 PiP，因此只可比较已完成的手动路径。

`config-deferred-20261028-230148` 和 `config-verified-20261028-230426` 的系统采集启动失败，仅应用日志可用，不用于合成器判断。`config-display-20261028-230603` 的应用触摸测试中途超时，完成的三个缩放区间可分析，不能称整轮通过。部分完整跟踪报告两组 `traced_buf_sequence_packet_loss`，告警与原始文件保留，不能称整条系统跟踪绝无缺失。

最终可见性修正版回归：`visible-fixed-landscape-20261028-232901`、`visible-fixed-portrait-corner-20261028-233503`。两种画幅各测手动和 HOME 两条路径，共 24 次播放中缩放、8 次暂停缩放、4 次返回原详情页，均通过会话、缓冲和实际 View 可见性检查。两个目录的完整系统文件均已与模拟器原文件校验 SHA-256 相同。

| 验证项 | 最终结果 |
| --- | --- |
| 系统合成器中的视频屏幕边界 | 32 个缩放区间均未出现空边界 |
| 视频输出重新绑定 / 销毁 / 改变尺寸 | 缩放区间均为 0 |

仍需区分统计口径：Window 的 UI 长帧没有全部消失；系统图层几何更新间隔在个别捏合/停顿阶段超过 100ms，不能凭这些记录宣称所有界面和动画零长帧。视频在缩放时实际连续提交且可见，是本轮视频停顿与裁切修复的验收依据；真机表现和电量消耗未在本轮测量。

## 官方资料

- [Android PiP 文档](https://developer.android.com/develop/ui/views/picture-in-picture)：缺失或不合适的 sourceRectHint 会触发系统内容覆盖层；需及时更新视频实际区域，视频支持 seamless resize。
- [SurfaceFlinger 跟踪配置](https://github.com/google/perfetto/blob/main/protos/perfetto/config/android/surfaceflinger_layers_config.proto)：本轮使用主动图层快照检查覆盖层可见性。
