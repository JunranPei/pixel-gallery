# SSIV / JPEG v7 稳定化计划

## 目的

把 `codex/ssiv-lite` 上已经验证有效的 SSIV 滑动改进与 JPEG v7 可寻址金字塔整理成可审计、可回退、可合并的实现，解决首轮未命中时的持续解码功耗，同时不破坏原图倍率、跨窗口索引共享、缓存和现有查看器交互。

本计划建立在修复前基线 `b9c3cbe0`（`perf(index): store JPEG pyramid as addressable tiles`）之上。

## 已确认的事实

- 旧的整层 JPEG 金字塔在 `sample=2` 首轮未命中时仍然昂贵：东汉图 85 次、平均 81 ms；政和图 69 次、平均 93 ms。上传降到约 4.4–5.3 MB 只降低了卡顿尖峰，没有消除整层区域解码成本。
- v7 已将 `sample=2/4/8...` 改为单文件内的独立 1024×1024 JPEG 块；`sample=1` 继续使用原图 seek index，不复制原图。
- 三星实测中的两个索引都是有效且新鲜的 v7，未出现 native/JPEG 错误。观察到的短生命周期对象回收说明仍有临时 Bitmap/字节数组分配，但没有证据表明存在内存泄漏。
- 当前单块读取仍会先解码为临时 Bitmap，再 Canvas 复制到结果 Bitmap；完全对齐单块时这次复制没有必要。
- 当前 `sample>=16` 使用抽点降采样，可能让细线、文字和规则纹理发生混叠。
- 当前 `Ready(bytes)` 无法区分 v2–v6 旧索引、v7 完整金字塔和 v7 seek-only 降级结果，因此界面可能把“索引可用”错误表达成“可寻址金字塔已经完成”。
- 创建、删除或替换索引后，已打开的 SSIV 会刷新 native 解码器，但不会自动重建瓦片网格；当前页的适屏预览也没有把索引能力变化作为缓存键。
- 当前发布流程先删除旧索引再重命名临时文件；进程中断时可能丢失原本可用的索引。结构校验对部分旧格式和 seek-only 文件也不完整。

## 不可突破的边界

- 不做三星、一加或任何单设备分支；所有策略依据图片、视口、索引能力和内存预算决定。
- 不关闭原有放大状态继承、相邻大图侧滑、原图倍率和瓦片浏览能力。
- 不把“停止加载”当作降低功耗方案；降低的是每次未命中的实际解码、复制和上传成本。
- 不自动创建索引，也不静默重建用户已有的旧索引。旧索引继续可用，但界面应如实提供“升级/重建”。
- 多窗口共用同一物理索引和缓存；任何窗口修改索引后，其他窗口下次绘制时必须能发现能力变化。
- 不根据一次功耗数字或单张测试图做定向阈值补丁；以解码次数、单次耗时、分配、瓦片层级和命中状态作为判断依据。
- 本轮不提交四个仅因 Windows 换行符被标记的 libjpeg vendor 文件。

## 本轮修复顺序

### 1. 索引状态与文件生命周期

目标：索引的状态、能力和磁盘文件必须真实可靠。

- 扩展状态信息，至少报告格式版本、是否具备独立可寻址金字塔、金字塔层数以及 seek-only/降级原因。
- v2–v6 旧索引继续解码，但不冒充 v7 完整优化；界面显示“升级/重建”，不自动执行。
- 完整校验 checkpoint、overview/pyramid 目录、数据边界和结束标记；截断文件不能返回 Ready。
- 构建结果先写入同目录临时文件并同步数据，再原子替换正式文件；不能预先删除旧索引。
- 清理超过安全时限的遗留临时文件，不触碰正在构建的文件。

验收：旧索引可读、截断索引被拒绝、失败构建保留旧索引、v7 seek-only 与完整 v7 状态可区分。

### 2. 运行中能力变化

目标：创建、删除、升级或移动 index 后，已打开页面不会继续使用过期网格或过期预览。

- 给解码能力增加轻量 revision/signature。
- SSIV 发现能力变化时使旧任务失效并重建瓦片网格，同时保留 scale、center、orientation 和手势状态。
- 适屏预览缓存键包含索引格式/能力签名，避免当前页继续持有旧预览模型。
- 跨窗口共享变化通知；不依赖某个窗口自己的 `imageIndexReady` 布尔值。

验收：图片保持打开时创建和删除 v7 索引，网格能在 1200 与存储块尺寸之间切换，视图位置不跳变；另一窗口也能在下一次绘制时同步。

### 3. v7 解码热路径

目标：降低首轮未命中的真实成本，而不是只推迟工作。

- 请求恰好覆盖一个存储块时直接返回解码 Bitmap，去掉目标 Bitmap、Canvas 和一次像素复制。
- 跨块请求继续只组合实际相交的块；边缘块不得扩张到完整 1024。
- 保持可见区优先、低层兜底、有界邻块预取和有界 LRU；不恢复整层 JPEG + `BitmapRegionDecoder`。
- Java `ByteArray` 仍是一个已知分配点；只有在证据显示它仍是主要成本时，才另做 JNI 直接解码到 Bitmap，避免提前扩大 native 改动面。

验收：单块路径只有一次 Bitmap 解码，无额外目标 Bitmap；跨块和边缘区域像素正确；首轮未命中不再出现旧 v6 的整层区域解码波。

### 4. 高层金字塔质量

目标：`sample>=16` 不再用抽点造成混叠。

- 保留 libjpeg 最高 1/8 DCT 缩放，再对 1/8 输出做流式面积/盒式降采样。
- 正确处理非整除尺寸、最后一行/列和 `sample=16/32/...`。
- 这是一次性索引构建成本；不得把完整中间层常驻内存。

验收：奇数尺寸和 sample 16/32 输出尺寸正确；细线/棋盘测试不发生固定相位抽样丢失；构建内存仍受现有上限约束。

### 5. 测试与文档

至少补齐：

- v6 整层兼容、v7 seek-only、v7 完整能力表达；
- 单块、跨块、四块交界、奇数尺寸和边缘块；
- EXIF 90/180/270；
- 截断 checkpoint、损坏目录/结束标记、替换失败回滚、遗留临时文件；
- 同一源并发 build/delete/open；
- 已打开 SSIV 的能力切换、网格对齐和旧任务失效；
- sample 16/32 降采样质量；
- 现有五项 instrumentation 测试与 JVM 单元测试回归。

同步更新 `indexed-jpeg/DESIGN.md`、SSIV README 和索引对话框文案，删除“只读小头部”“只扫描原图一次”等已经失真的描述。

## 后续独立工作，不混入本轮

- 构建器目前会为每个层级重新打开并解码源 JPEG，且写入前会在内存中保留所有编码瓦片。后续改为流式临时区/两阶段目录写入，单独测量构建耗时、峰值内存和失败恢复。
- `length + lastModified` 不是强源身份。后续索引格式可加入有界内容指纹，必须以兼容格式升级实现，不能临时塞进 v7。
- 所有 native 模块的 16 KB page-size 兼容是发布级工作，覆盖 JPEG/PNG/WebP/HEIF/RAW/TIFF/BMP/JXL，单独修改构建配置并检查 ELF；不作为本轮 JPEG 性能结论的一部分。
- `feature-3..codex/ssiv-lite` 的历史包含构建恢复、SSIV、PNG、JPEG、查看器和测试打包。稳定合并时从 `feature-3` 整理为逻辑提交，不直接把整串实验提交当作最终历史。

## 验证矩阵

每轮测试都区分以下状态，不能把后续缓存命中当成首轮改善：

| 场景 | 索引状态 | 关注指标 |
| --- | --- | --- |
| 首次适屏 | 无索引 / v6 / v7 seek-only / v7 完整 | 解码层级、次数、总时长、临时分配 |
| 浅放大 | v7 首轮未命中 / 第二轮命中 | 单块耗时、块数、上传字节、GC |
| 高倍率 | sample=1 seek index | 原图区域解码回归、瓦片边界 |
| 大图侧滑 | 未放大 / 保持放大 | 双页并发工作、帧时间、解码波 |
| 运行中变更 | build / delete / rebuild / relocate | 网格重建、视图保持、跨窗口同步 |

设备功耗由用户在拔线状态下判断；ADB 只收集应用日志、解码事件、帧时间和内存分配，不用整机充电状态替代用户实测。

## 提交与回退规则

1. 本文档单独提交，形成修复前基线。
2. 状态/校验/原子发布作为一个正确性提交。
3. 运行中能力变化作为一个生命周期提交。
4. 单块直返与过滤降采样分别提交，便于 A/B。
5. 测试和失真文档随对应行为提交，不用一个大提交掩盖多个变量。
6. 每个阶段先检查 staged diff，四个 vendor 换行文件不得进入提交。
7. 任一阶段验证失败，只回退该逻辑提交，不回退用户的其他分支工作。
