# 普通模式下的应用内图片加载实验

设备为一加 CPH2745。通过电池界面切回均衡模式，测试前后 `high_performance_mode_on=0`。仍使用独立无缓存诊断包 `com.pixel.gallery.loadtrace.nocache`；正式相册未替换。

## 解码线程优先级与系统性能提示

测试 APK 新增只读取指定原文件的 `ImageSchedulingProbe`。4 张原图，各以 nice 9、nice 0、nice -2、nice 0 加 PerformanceHintManager 会话四种方式运行，每种每图 4 次，共 64 次；每轮轮换执行次序。只调用原有原生 decodeFit，目标 1272×2772，位图结果立即释放，没有引入缓存。该测试是解码函数测试，不是界面完成时间。

| MediaStore ID | nice 9 | nice 0 | nice -2 | nice 0 + 短时性能提示 |
|---|---:|---:|---:|---:|
| 218912 | 209.13 ms | 208.46 ms | 207.75 ms | 207.44 ms |
| 218910 | 212.45 ms | 211.39 ms | 213.13 ms | 210.76 ms |
| 218917 | 177.99 ms | 178.70 ms | 176.52 ms | 176.66 ms |

以上为每组中位数。性能提示会话均创建成功；本次只测试每次解码创建、完成后报告并关闭的短时会话。此配置及优先级调整没有明显改善，未将它们作为正式优化。

有效结果来自 `scratch/image-scheduling-probe/direct-full-quoted.txt` 和提取后的 `results.json`。部分早期自动采集被中止，未用这些中断轨迹推算该组执行频率。

## 去掉原生预览后的 CPU 二次缩放

原路径先生成原生采样位图，再由 Glide FitCenter 生成适屏大小位图。实验将原生预览的 Glide transformation 禁用，由 ImageView 在显示时执行适屏缩放。原生解码本身和方向处理没有更改，Ultra HDR 分支保持原样。

功能由 `nativeGpuFitProbe=true` 控制，只允许在 `nocachetrace` 构建中使用，生成 `NATIVE_GPU_FIT_PROBE=true`；默认值为 false。包内全部无缓存策略继续启用。

三张原图均为 3750×5000，原生输出均为 1875×2500。基线共打开 7 次，实验版共打开 6 次，每张至少各 2 次。两侧所有完成来源均为 LOCAL。以下为每个文件各自的中位数。

| MediaStore ID | 基线完整预览请求 | 实验版完整预览请求 | 基线原生工作结束至预览就绪 | 实验版对应阶段 |
|---|---:|---:|---:|---:|
| 836065 | 228 ms（3 次） | 165.5 ms（2 次） | 67 ms | 1 ms |
| 836063 | 204.5 ms（2 次） | 143.5 ms（2 次） | 67 ms | 0.5 ms |
| 836062 | 225.5 ms（2 次） | 162.5 ms（2 次） | 67 ms | 0.5 ms |

原生解码耗时未改善：三张的基线中位数分别约 159.5、135.9、156.3 ms，实验版约 161.8、141.1、159.9 ms。缩短来自原生解码结束后的路径。

这些是请求与预绘制计时，没有重新关联 SurfaceFlinger 的实际呈现时间。基线与实验版适屏截图均已查看，内容位置和比例一致；实验版在一张样本上完成双击放大，捕获平台区域解码及 `tilesReady=true`，放大截图也已查看。尚未覆盖旋转 JPEG、ICC 回退、HDR 和多窗口的完整回归。

较早一次自动界面对照没有逐次确认前台应用，未取得有效相册请求，该次日志 `grid-baseline-events.txt` 被排除。之后的基线和实验对照都在每次点击前检查前台 Activity 为诊断包。

## 内存及构建状态

三张样本最终保留的预览位图由 1272×1696、8,629,248 字节变为 1875×2500、18,750,000 字节，每张增加约 10.1 MB。原生中间输出保持不变，实验取消了额外 CPU 缩放和对应的输出位图分配，但最终保留的预览更大。正式版默认开关保持关闭，尚未将这项试验推广为全格式优化。

首次 assembleRelease 在完成代码编译后，Java 本地内存分配失败，Gradle 守护进程退出。降低构建资源后，`:app:packageRelease` 成功；未将其写成完整 lint 通过。诊断 APK 已安装到一加。

文件为 `artifacts/PixelLoadDiagnostic-gpu-fit-nocache.apk`，SHA256 为 `e6db5abdf193ac2b4840fbdca7f4f393a6b54d0a6612a14ac70d6d536c90f296`。

测试期间临时使用的 USB 保持亮屏设置已恢复为原值 0，一加高性能模式保持关闭。截图、日志和逐图数据位于 `scratch/image-scheduling-probe/`，其中 `gpu-fit-comparison.json` 为最终统计。

## 后续低内存与黑帧实验

用户不接受较大预览的内存增长，后续改用逐行解码时直接缩放到最终适屏尺寸，保留原先 8,629,248 字节的三张样本输出。另对用户指定的 11 张 JPEG，在现有正式版中记录重复打开黑帧，再以保留过渡图的窗口交接实验进行录屏复测。完整结果、内存采样与 APK 校验见 [指定 11 张 JPEG 的黑帧与低内存交接验证](image-load-eleven-jpeg-blackframe-20261114.md)。当前安装的独立诊断包已采用后续低内存实现；本节之前的较大位图实验只作为历史对照留存。
