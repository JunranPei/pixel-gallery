# 多窗口历史版本内存对照

目标：在相同媒体记录、图片尺寸及窗口操作下比较用户指定的六个历史节点，定位内存及后台 Activity 回收回归。保留 4.3.3.2 为稳定基线，当前未提交优化独立作为修复版测试，不混入历史基线。

## 隔离与方法

- 源码使用 git archive 分别取出到 scratch/version-memory-comparison/4359、4364。
- 独立测试包 com.pixel.gallery.memory4359、com.pixel.gallery.memory4364，只在 emulator-5562 运行。
- 同一测试驱动 VersionWindowMemoryInstrumentation.kt；实际 MainActivity、ACTION_VIEW、图片解码及界面，不替换应用画面。
- 131014 条媒体记录、179 个测试相册文件、1856 × 2304 JPEG；用应用自己的 Room 表。测试时持有媒体写锁，阻止系统图库同步覆盖隔离夹具。
- 两版使用相同 x86_64 原生库文件；对应 C/C++ 源码在两提交间无变化，构建配置调整及文件散列保存在各目录 comparison-build.json。
- 开 12 个详情任务，再开主 grid，通过真实菜单打开 Quick Sort，使用设置 API 按相同次序写入六个目标相册。另做 12 次群组设置写入；旧版没有群组功能，仍接收相同原始偏好写入。
- 每 10 ms 采样 Java 堆，阶段结束记录 Java 堆、native heap、PSS、累计分配、GC 次数、Activity 生命周期与详情图像可见状态变更。测试不使用截图识别。
- 建库结束请求一次 GC，真实窗口阶段不强制 GC。返回首个任务检查是否重建；记录没有强制杀后台的自然行为。

## 建库条件统一及堆对象核查

旧版没有 readRefreshes，而早期新版夹具在建库时调用 hold/close。即使采用单事务写入，这个额外触发仍导致两次相同内容的 Room 读取。为比较正常加载后的窗口占用，从 4356before/4356after 及 4364-weak-bulk2 起默认关闭夹具的 seedGate；4332 和 43411 原本没有此调用。原始 gated 结果保留，不能把它额外保留的一份数据都算成正常启动回归。

使用真实 Android 堆快照另做建库诊断（不含窗口负载，不作为帧耗时测试）：

| 当前 4.3.6.4 准备方式 | MediaEntry 实例数 | 不同 path/URI/MIME String 引用数 |
| --- | ---: | ---: |
| seedGate=true，4364-seed-gated-diagnostic | 262028 | 各 262028 |
| seedGate=false，4364-seed-ungated-diagnostic | 131014 | 各 131014 |

读取的是相同 131014 行；额外一份为独立解码出的完整媒体对象及字符串。HPROF 计数脚本 hprof_counts.py 完整解析记录边界并在未知记录类型时报错；Android root 类型对照 ART 官方源码：https://android.googlesource.com/platform/art/+/06db56c39997b1bb1e69a3c5f2ba960dcd13e11a/src/hprof/hprof.h 。这里只列实例与字段引用计数，不把 payload 大小当作对象完整占用或支配内存。

待验证补充修复：Room 读取结果进入 combine 前按 MediaEntry 全字段相等过滤，避免 combine 保留新一代相同对象、StateFlow 又保留旧一代对象。真实批处理也使用该刷新闸门，所以另保留 gated 机制作为回归用例。该修复加入 patched，indexonly 仍只修改索引共享。

## 重复刷新：实例总数与实际持有链核对

`patched-seed-gated-diagnostic` 的原始快照仍包含 262028 个 MediaEntry，因此追加 `hprof_owners.py` 逐对象引用检查。实例总数包含尚未回收的不可达对象，不等于存活数量。解析实例及父类字段、数组引用、静态引用、GC 根；反向追踪时排除 Reference.referent 弱引用，并逐步追到应用根。

抽取相同 contentId=10000000 的两份对象：

- 原版：第一份经 ArrayList → StateFlow → MediaRepository.allEntries → Hilt → Application；第二份经 Arrays.ArrayList → combine 最新值数组 → 活动协程 Job → allEntries → Hilt → Application。两份均有强引用根。
- 加读取结果过滤后：第一份仍由 allEntries 持有；第二份的所有反向祖先只有 8 个，均为已完成的读取/比较过程对象，无进一步持有者或 GC 根。这一份已可回收。

因此原先“过滤后依然保留两份”的初判不成立，过滤已去掉第二份长期持有；实际快照中还存在临时对象。额外尝试的独立 MutableStateFlow 读取方案已撤回，采用 map 后 distinctUntilChanged 的小改动。

证据：4364-seed-gated-diagnostic.owners.json、patched-seed-gated-diagnostic.owners.json。堆快照仅用于测试包的合成数据。官方堆分析说明亦区分 GC 前快照中的不可达实例：https://github.com/google/perfetto/blob/main/docs/visualization/heap-dump-explorer.md 。

随后用相同程序等待刷新结束并执行三次 GC，再采集快照，补证存活数量：

| 同样 131014 行，重复刷新后 | Java 堆 MiB | MediaEntry 实例数 |
| --- | ---: | ---: |
| 4364-gated-postgc1 | 106.0 | 262028 |
| patched-gated-postgc1 | 58.2 | 131014 |

`hprof_owners.py` 还核对了所有实例字段长度（含父类）与 HPROF 记录长度一致，原始快照、解析结果和失败尝试均保留。

## 真实内容变化时的增量对象复用

只改一条记录也会让 Room 返回整库新 MediaEntry 及字符串；背景窗口的旧浏览索引仍持有上一代，前台构建和查看器序列更新又使用新一代。这与“重复读取完全相同内容”不同，不能用 distinctUntilChanged 过滤实际更改。

追加 `reuseUnchangedMediaEntries`：整份内容一致时复用旧 List；内容变化时，按原位置或 contentId 匹配，但仅在所有存储字段均相同时复用旧 MediaEntry。保持查询的新顺序、新增、删除和真正修改的值；不修改旧窗口持有的对象。时间排序移动一条记录时，其余 131013 条仍共享，不再完整保留两套相同记录。新增 5 项模型测试，覆盖完全相同、更改后重排、增删、每个存储字段、编辑后恢复；原失败的真实窗口用例继续重跑。

这次修复的 44 项 JVM 测试全部通过：MediaEntrySnapshotsTest 5、MediaBrowseIndexCacheTest 7、MediaBrowseIndexTest 11、CollectionCoverMemoryTest 5、CollectionCoverTest 3、AlbumGroupingTest 13。`patched-gated-postgc2` 重复刷新后 GC 实测 58.1 MiB / 131014 个 MediaEntry。
